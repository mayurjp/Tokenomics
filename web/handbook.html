01

Token fundamentals & the procurement view

Everything downstream — routing, caching, budgets, dashboards — is a response to four facts about how tokens are counted and priced. Start here or nothing else has units.

Words are not tokens

A tokenizer splits text into subword pieces, not words. The common rule of thumb: 1,000 words ≈ 1,300 tokens, a 30% inflation that varies by language and format — dense, non-English scripts and machine formats both tokenize worse than plain English prose.

Same sentence, different tokenizer bill
RenderingApprox. tokensvs. English
English — "Track every dollar the model spends."71.0×
Hindi — same meaning, Devanagari script131.9×
Japanese — same meaning152.1×
As a JSON field: {"instruction":"Track every dollar the model spends."}162.3×
Cost trap

Estimating token spend by counting words in the source language systematically underbids non-English and structured-data workloads by 2× or more.

Input and output are not the same product

Every provider prices output higher than input — in this reference's rate card, 5× on Tier A, 5× on Tier B, 4× on Tier C. A request's cost split is rarely 50/50; it follows how much the model had to generate versus read.

Per-request costcost = (input_tokens ÷ 1,000,000) × rate_in + (output_tokens ÷ 1,000,000) × rate_out

On reasoning models, the "thinking" trace is produced token-by-token like any other output and billed at the output rate — then discarded before the answer is returned. The same prompt at two reasoning efforts:

Memory is resent, not remembered

The model is stateless. Every turn re-sends the full transcript so far — the conversation's input cost is the sum of every prior turn, every time. Two message-size scenarios over 10 turns, Tier A:

At Tier A rates, that realistic 10-turn conversation costs 52,500 input tok × $3/1M + 8,000 output tok × $15/1M ≈ $0.28. Now drop one 250,000-token PDF into context and resend it every turn, unmanaged:

Cost trap

A file dropped into chat context is not read once — it is re-billed on every subsequent turn until the conversation ends or the history is managed. Chapters 2 and 3 cover the fixes (retrieval instead of stuffing, and compaction).

Why this reads like a utility bill, not a seat license

Token spend is metered, like electricity or gas — usage varies by the minute, not the month, and a single workload can spike spend well past a forecast built on averages. Treat it accordingly: variance bands and hard caps, not a flat per-seat line item. Chapter 5 works a heavy-user example; Chapter 6 covers the alerting that catches it before the invoice does.

02

The layered cost-optimization stack

Eight techniques, each intercepting a request at a different point before it reaches the most expensive model. None of them are alternatives to each other — a mature system runs all eight in sequence.

1 — Semantic caching

Embed the incoming question, compare it against embeddings of past questions, and return the stored answer when similarity clears a threshold — typically cosine similarity ≥ 0.90. "What's our refund window?" and "How long do customers have to request a refund?" embed close enough to hit; "What's our refund window in the EU?" usually does not, since the jurisdiction changes the answer. A hit costs one embedding call and zero generation calls.

2 — Model routing

Route by task shape, not by default. The same 500-in/300-out task across all three tiers:

One task, three tiers
TierCostvs. flagship
Tier A — flagship$0.006001×
Tier B — mid$0.001603.75× cheaper
Tier C — light$0.0002623.5× cheaper

3 — Model cascading

Attempt on Tier C; escalate to Tier A only when a validator (confidence score, schema check) fails. At a realistic 20% escalation rate, the escalated cases pay for both attempts:

Expected cost per requestE[cost] = cheap_cost + (escalation_rate × flagship_cost) = $0.00026 + (0.20 × $0.00600) = $0.00146 ← 4.1× cheaper than always-flagship ($0.00600)

4 — Prompt caching

A 2,000-token system prompt reused across 50 calls, cached input at 10% of Tier A's rate:

Uncached, 50 calls$0.300
Cached after call 1$0.035
Reduction88%

5 — Context compaction

Summarize older turns into a running digest instead of resending them verbatim. This is the direct fix for Chapter 1's 60,500-token conversation: summarizing every 5 turns caps the resent history near a fixed size instead of letting it grow linearly with turn count — the tradeoff is that a summary is lossy, and the detail it drops is invisible until someone asks for it.

6 — Batch processing

For work nobody is waiting on synchronously, batch endpoints typically run at roughly half the interactive rate, in exchange for completion measured in minutes to hours instead of seconds. Rules it out the moment a user is staring at a spinner.

7 — Token-efficient prompting

Structured output strips the conversational wrapper around an answer:

Same extraction task, prose vs. JSON
FormatOutput tok.
"Sure — the customer's name is Priya Nair, their order number is 48213, and it shipped on the 14th."26
{"name":"Priya Nair","order":48213,"shipped":"14th"}14

8 — Observability / FinOps telemetry

None of the previous seven are verifiable without one event logged per call. Minimum viable shape: model, tokens_in, tokens_out, cache_hit, cost, feature_tag, team_tag, outcome. This is the raw material Chapter 6's dashboard consumes — a technique you can't measure is a technique you're guessing about.

Cost trap

Implementing one layer — usually caching, because it's the easiest — and calling the architecture "optimized" leaves the other seven multipliers untouched. They compound; skipping most of them leaves most of the 70% on the table.

03

Agentic FinOps

An agent turns one user request into a loop — plan, retrieve, act, validate — and each hop is its own billable call. Budget the workflow, not the first call.

The naive-estimate trap

A 5-step loop where each step's prompt includes the growing history of every prior step:

Tokens per step, cumulative history appended each time
StepTokens this stepCumulative
1 — plan150150
2 — retrieve450600
3 — act9501,550
4 — validate1,6503,200
5 — respond2,5505,750
Budgeted (step 1 only)$0.0009
Actually spent (blended ~$6/1M)$0.0345
Underestimate38×

The RAG trap, inside the loop

A retrieval step that injects a whole 4,000-token chunk when the answer lives in roughly 300 of them:

Relevance densitydensity = useful_tokens ÷ injected_tokens = 300 ÷ 4,000 = 7.5%

The other 92.5% — 3,700 tokens — is paid for at the input rate on every call that reuses this retrieval step: $0.0111 wasted per call at Tier A, before the model even starts answering.

The reliability multiplier

Retries and multi-agent debate protect quality by repeating work — and repeated work is repeated billing:

Expected cost under retrieseffective_cost = base_cost × (1 + retry_rate)
Base call $0.0060 (Tier A), three retry rates
Retry rateEffective cost
10%$0.0066
30%$0.0078
60%$0.0096

A 3-way parallel debate is the same shape with a fixed multiplier instead of a rate: effective_cost = base_cost × N — three calls in flight regardless of whether any of them fail.

Selective memory, scored not summarized

Rather than replaying full history or blindly summarizing it, score each prior turn on recency + relevance to the current step + an explicit pin flag, and carry forward only what clears a threshold. On the 5-step loop above, scoring typically holds the resent context near the size of steps 1–2 instead of letting it reach step 5's 2,550 tokens — the saving compounds every subsequent step, not just the current one.

Budgets as a design input, not a monitoring afterthought

  • max_output_tokens — a hard ceiling per step, set before the loop runs.
  • max_retries — a count, not an implicit "keep trying."
  • cost_ceiling_per_task — the number Chapter 4's circuit breaker actually enforces.
Cost trap

Sizing an agentic feature's budget off a single representative call, then discovering in production that the loop routinely runs 5–10 steps deep, each carrying more history than the last.

04

Engineering the budget controller

A circuit breaker for autonomous loops: not a monthly cap, a per-task guard that trips mid-flight.

The runaway-loop failure mode

Left unbounded, a validation loop retries the same failing step, appending the failure to history each time — the same superlinear growth as Chapter 3's agent loop, except now it has no natural exit. Ten unchecked retries following that growth curve run past 25,000 tokens before anything stops it.

Circuit-breaker logic

Guard, checked after every stepsession_cost += step_cost if session_cost >= budget_ceiling: # e.g. $0.15 / task halt(reason="budget_exceeded") return escalate_to_human_or_fallback()

The ceiling is a business number, not an engineering one — it's whatever the completed task is worth, with margin. A support-ticket resolution budgeted at $0.15 that trips the breaker at step 4 has failed cheaply; the same loop left unbounded fails expensively.

Asymmetric tiering inside the loop

A 4-step loop — draft, extract, re-check, final judgment — run all-flagship versus tiered, with only the last step reserved for Tier A:

4-step loop: all-flagship vs. tiered execution
StrategyCost
All Tier A$0.0240
Tier C ×3 (draft, extract, re-check) + Tier A ×1 (judgment)$0.0068
Savings3.5×, same final-judgment model

Dynamic replanning

When a step fails, replan from a trimmed context — the goal plus the specific failure reason — rather than the full transcript of everything tried so far. Replanning against the full failed history means every subsequent attempt pays to re-read its own prior mistakes; replanning against a two-line failure summary does not.

Cost trap

A retry budget with no cost ceiling still bounds attempts, not spend — five retries against a growing context can cost more than fifty against a flat one. Bound the dollar amount, not just the attempt count.

05

Macro ROI & hybrid architecture

Zooming out from any single call: does the intelligence generated cost less than the outcome is worth, and does the org's forecasting model account for how usage-based spend actually behaves?

The seat-based pricing illusion

A department budgets AI spend the way it budgets seats — a flat number per person per month. Usage-based pricing doesn't hold that shape:

Typical daily department spend$50
One heavy user, 5,000 requests in a day$500
Multiple of the daily budget10×, from one person

Over-engineering a trivial task

A binary classification — 50 input tokens, 5 output tokens — run on flagship vs. light tier at volume:

5,000,000 calls / month, identical output either way
TierCost / callCost / month
Tier A — flagship$0.000225$1,125
Tier C — light$0.0000105$52.50

$1,072 a month spent for zero quality difference — the task carries no reasoning to pay a reasoning-grade price for.

Cost-per-token vs. cost-per-completed-task

The metric that matters to the businesscost_per_completed_task = total_cost_across_all_attempts ÷ successful_outcomes

100 tasks at $0.006/call, 85% first-try success; of the 15 failures, 12 succeed on retry and 3 escalate to a flagship fallback at $0.024:

Cost per completed task, worked
PathCountCost
Succeed on first attempt85$0.510
Succeed on retry12$0.090
Escalated to flagship3$0.072
Naive cost / call$0.0060

Hidden markup+15.5%

Hybrid architecture

Blend a frontier API model for the reasoning-heavy edge of the workload with a self-hosted, quantized model for its high-volume, routine core. The API side buys elastic capacity and stays current with model quality; the self-hosted side buys cost stability that doesn't move with a provider's pricing page — at the cost of the operational burden of running it. The right split follows the workload's actual volume curve, not a blanket preference for either side.

Cost trap

Tracking only cost-per-token hides retries and escalations inside a rounding error — the number that matters for ROI is what a finished outcome cost, including every attempt it took to get there.

06

Enterprise governance & telemetry

A monthly cloud invoice answers "how much," never "which feature, and was it worth it." Governance is the layer that makes those answerable.

The black-box invoice

An aggregate monthly number — "$14,200 in model spend" — carries no information about which feature drove it, whether that feature is profitable, or whether the number is trending up because of growth or because of waste. The fix is not a bigger number; it's the same number, broken down.

Same $14,200, broken down by feature
FeatureSpendResolutionsCost / resolution
Support triage$6,10041,000$0.149
Document summarizer$4,9003,200$1.531
Internal search assistant$3,20028,500$0.112

The aggregate number hides that the summarizer costs 10–13× more per completed unit of work than the other two features — the number worth investigating never shows up until it's broken out.

Minimum viable telemetry event

One row per call{ model, tokens_in, tokens_out, cache_hit, cost, latency_ms, feature_tag, team_tag, outcome: "success" | "fail" | "retry" }

What to derive from it

  • Cost per resolved task — spend ÷ successful outcomes, per feature.
  • Cache hit rate — the leading indicator that Chapter 2's caching layer is actually engaged.
  • Tokens per request, trended — catches prompt bloat creeping in before it shows up in the bill.
  • Spend per team, over time — attribution that survives a reorg, if the tag does.

Alerting design

Example thresholds
SignalTriggerAction
Daily spend>2× the 7-day rolling averagePage the feature owner
Cache hit rateDrops below 60% for an hourCheck for a cache-key regression (Ch. 7)
Cost per resolutionRises 25% week-over-weekReview recent prompt changes
Cost trap

Instrumenting spend without a feature or team tag produces a dashboard that can say a number went up, never why — which is the same blindness as the monthly invoice, with better graphics.

07

Prompt caching internals

The mechanism under Chapter 2's ~90% discount, and the one silent bug that switches it off.

Prefix hashing

Providers commonly hash a prompt in fixed-size blocks from the start (a 256-token boundary is a widely reported figure) and route matching requests to a server still holding that prefix's computed state. The requirement that follows directly: the first block of tokens must be byte-identical across calls, or the hash — and the cache hit — never happens.

What's actually cached

Underneath the hash sits the GPU's key/value cache — the intermediate attention state computed for the prefix, held in memory rather than recomputed. A cache hit isn't "skip a network round trip"; it's "skip re-running the model over tokens it has already processed," which is where the discount comes from — genuinely less compute, not a lookup shortcut.

The invalidation bug

The single most common way to silently lose the discount: a dynamic value — a timestamp, a user's name, a request ID — placed at the top of the system prompt. It changes every call, which changes the prefix hash, which invalidates the entire cached block behind it, no matter how large and stable the rest of the prompt is.

Same system prompt, dynamic value moved
StructureCache behavior
"Request at {timestamp}. You are a support agent…[3,000 stable tokens]"Never hits — hash changes every call
"You are a support agent…[3,000 stable tokens]. Request at {timestamp}."Hits — stable prefix hashed once

TTLs differ by provider

Cached prefixes expire. As reported at the API layer, retention windows differ meaningfully by provider — commonly cited figures are on the order of an hour for some providers and single-digit minutes for others. A workload with gaps longer than the shorter window needs to actively re-warm the cache (a cheap keep-alive call) or it silently falls back to full price between bursts of traffic.

Worked: a 20-step agent session

A 3,000-token system prompt + tool definitions, resent on every one of 20 steps:

Uncached, 20 steps$0.180
Cached after step 1$0.026
Reduction85%
Cost trap

A cache hit rate that quietly drops to zero after a code change usually traces back to one variable moved to the wrong end of the prompt — it fails silently, at full price, with no error to surface it.

Tactical token reduction

Small, code-level changes that compound at volume — none of them architectural, all of them cheap to ship.

Strip conversational filler

An unconstrained model pads answers with acknowledgement and sign-off text that carries no information:

Same code answer, with and without filler
ResponseTokens
"Sure, here is the code you requested: […] Hope this helps! Let me know if you have any other questions."215
"[…]" (system prompt: answer only, no preamble or sign-off)200

15 tokens of pure filler, ~7% of that response — at 1,000,000 responses a month, $225 spent on "Sure, here is" and "Hope this helps," at Tier A's output rate.

Minify JSON keys

Same field, two schemas
KeyTokens
customer_first_name_and_last_name9
name1

8 tokens saved per field. At 10 fields per record and 1,000,000 records a month, that's 80,000,000 output tokens — roughly $1,200 — recovered purely by mapping short wire-format keys back to descriptive names in application code, where the model never has to pay to read them.

Chunk the workflow instead of one monolithic call

Extract, reason, and format in one flagship call versus the same work split across three smaller, tier-matched calls:

One 3-stage task, monolithic vs. chunked
ApproachCost
One Tier A call — extract + reason + format$0.0114
Tier C extract → Tier A reason → Tier C format$0.0033
Reduction3.5×, same final quality on the step that needed it
Cost trap

None of these three fixes require a new architecture — they're the ones a team skips because each one looks too small to matter, right up until it's multiplied by volume.

Embeddings & vector store costs

Semantic caching (Ch. 2) and RAG (Ch. 3) both lean on an embedding step that rarely gets its own line in a budget — until the corpus grows and the "hidden data layer" becomes the majority of infra spend.

Embedding is priced separately, and much lower

Embedding models are smaller and cheaper than generation models — in this reference, $0.02 per 1M tokens, roughly two orders of magnitude below Tier A generation. That gap is exactly why it's easy to under-budget: each individual call looks free.

Embedding costcost = (tokens_embedded ÷ 1,000,000) × $0.02

Indexing a corpus once

10,000 support documents, averaging 500 tokens each:

Tokens embedded5,000,000
One-time cost$0.10

The cost that compounds: query embedding at volume

Every RAG lookup and every semantic-cache check embeds the incoming query too — small per call, but it runs on every request, not once:

Query embedding at ~20 tokens/query
Queries / dayTokens / dayCost / month
10,000200,000$0.12
1,000,00020,000,000$12.00

Cheap even at a million queries a day — the trap isn't the per-query rate, it's multi-query retrieval (expanding one user query into 3–5 reformulated sub-queries to improve recall), which multiplies this line directly: 5× the sub-queries is 5× this cost, before a single generation call runs.

Storage isn't token-priced, but it isn't free

A 1536-dimension float32 vector is about 6 KB. A managed vector store charges by storage and query volume, not tokens — illustratively, around $0.25 per GB-month:

Storage at scale
VectorsSizeCost / month
1,000,000~6 GB$1.50
100,000,000~600 GB$150

The reindex bill nobody schedules for

Switching embedding models — a newer one, a different dimensionality — means every existing vector is now incompatible and the whole corpus must be re-embedded, not just new documents:

Corpus10M docs × 800 tok
Tokens to re-embed8,000,000,000
One-time cost$160

The dollar figure is modest; the trap is elsewhere — this is hours of batch processing and a cutover window, not something to discover mid-incident because a model was swapped casually.

Cost trap

Embedding costs are individually invisible and collectively real: nobody notices the query-embedding line until multi-query retrieval or a corpus-wide reindex turns it into the largest single item in the infra bill.

Multimodal & long-context economics

Two separate mechanisms, both underestimated for the same reason: neither charges by the thing you'd naturally count — pixels, or turns of context.

Images are billed in tiles, not pixels

A common tiling scheme: a fixed base charge, plus a fixed charge per 512×512 tile the image is sliced into. Resolution decides tile count; tile count decides the bill.

Image tokenstiles = ceil(width ÷ 512) × ceil(height ÷ 512) tokens = 85 + (tiles × 170)
100,000 product photos, one full pass, Tier A input rate
ResolutionTilesTokens / imageTotal tokensCost
512 × 512125525,500,000$76.50
1024 × 1024476576,500,000$229.50

Downscaling to the resolution the task actually needs — before upload, not after — is a 3× saving here with no code path more complex than a client-side resize.

Long context costs compute quadratically, not the invoice linearly

Self-attention compares every token to every other token, so the underlying compute for a context of length N scales with N² — a 100k-token context is roughly 100× the compute of a 10k one, not 10×. Providers absorb much of that behind a per-token price that scales far more gently, which is exactly why the cost is easy to underestimate: the bill looks linear even where the compute, and often the latency, does not.

Same request shape, context length only
ContextRelative computeWhat the user notices
10k tokens1×baseline latency
100k tokens~100×materially slower time-to-first-token

This is the mechanical reason RAG (Ch. 3) and context compaction (Ch. 2) pay off twice — they don't just cut the token bill, they cut the quadratic term driving latency.

Cost trap

Sending the maximum context window "just in case it's needed" pays the quadratic compute cost and the latency cost on every call, for information the model may never use — retrieve what's relevant instead of forwarding everything available.

12

Case studies

The worked numbers above are illustrative by design — deliberately round, so the arithmetic teaches the mechanism. These are reported outcomes from real deployments, included to show the same mechanisms holding up at production scale.

Prompt caching — Anthropic & Notion

Notion passes large volumes of user workspace data as context into its AI assistant. Implementing prefix-based prompt caching (Ch. 7) reportedly cut time-to-first-token by 50% and API costs by 60%.

Confirms: the ~85–90% cached-token discount in Ch. 2 and Ch. 7 isn't a lab number — it holds on real, large, per-user context.

Semantic caching — Zilliz / GPTCache

Zilliz, makers of the Milvus vector database, report that in enterprise B2B applications, up to 40% of user queries are semantically redundant. Layering GPTCache on top of an LLM pipeline reportedly cut API bills by nearly half.

Confirms: the semantic-caching mechanism in Ch. 2 targets a real, large share of traffic in support/FAQ-shaped workloads, not an edge case.

Prompt compression — Microsoft LLMLingua

Microsoft Research's LLMLingua algorithmically compresses prompts 2–3× before sending them to GPT-4, reportedly preserving entity-extraction accuracy while cutting directly into the (then) $0.03/1k-token inference cost.

Complements Ch. 8: where tactical reduction edits the prompt by hand, compression automates the same idea algorithmically for large, extraction-shaped documents.

Unmanaged agent history — Microsoft AutoGen

Engineers running Microsoft AutoGen in production found that unmanaged agent histories caused context windows to balloon within roughly 10 turns, forcing them to implement strict state-pruning to keep the system economically viable.

Confirms: Ch. 3's growth curve and Ch. 4's circuit breaker aren't a hypothetical failure mode — this is the same shape hitting a real multi-agent framework in the field.

Speculative decoding — Google DeepMind / Gemini

Google DeepMind's Gemini infrastructure reportedly uses a small ~1B-parameter draft model alongside a ~70B target model, increasing tokens-per-second by ~2.5× with no change to the final output.

A reminder that not every lever in this handbook is about the dollar figure — some, like this one, buy latency at a fixed infrastructure cost rather than trading quality for price.

Cost trap

Treating any single number above as a guarantee for a different workload — these are reported outcomes under specific traffic shapes, not universal multipliers. Measure your own before/after; use these as evidence the mechanism works, not as a forecast.

Rollout playbook

The chapters above are a reference, not a sequence — this is the sequence. Five stages, each one a prerequisite for the next to pay off.

Adoption stages
StageShipYou're ready to move on when
0 — No visibilityNothing yet — this is the starting stateYou only know the monthly total (Ch. 6)
1 — InstrumentPer-call telemetry: tokens, cost, cache hit, feature/team tag (Ch. 6)You can name your three most expensive features by cost, not guess
2 — CachePrompt caching on stable prefixes, semantic caching on repeated questions (Ch. 2, 7)Cache hit rate is dashboarded and holding above target
3 — RouteModel routing / cascading by task shape, now that traffic is tagged (Ch. 2)Trivial tasks are confirmed off the flagship tier
4 — BoundOutput caps, retry budgets, circuit breakers on agentic loops (Ch. 3, 4)No task can spend past its ceiling, even mid-incident
5 — GovernDashboards, spend alerts, cost-per-outcome as the reported metric (Ch. 5, 6)ROI conversations use cost-per-outcome, not cost-per-token

Why this order, specifically

Caching before routing, because a cache hit is free regardless of which tier would have served it — optimizing routing on traffic that should have been cached is solving the wrong slice first. Routing before bounding, because you need to know what a normal call costs before you can set a sane ceiling for an abnormal one. Bounding before governing, because a dashboard that watches an unbounded system just reports the incident after it happens instead of prevents it.

This week, not this quarter

  • Tag one feature. Add feature/team tags to your highest-volume LLM call site and start logging cost per call — the smallest version of Stage 1.
  • Find one static prefix. Locate the system prompt or reference document resent unchanged on every call, and check whether it's actually hitting the cache.
  • Price one worst case. Pick your riskiest agentic loop and compute what it costs if every step fails once — Ch. 4's ceiling starts as a number on paper before it's a line of code.
